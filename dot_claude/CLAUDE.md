# Python 環境依賴

Python 專案若未明確指定套件工具，一律使用 uv 處理。

# Bash 指令呈現方式

多步驟指令（用 `;`、`&&` 串接，或 for loop）要排版成多行，不要擠成一行，方便 review。

多個步驟彼此獨立時（例如唯讀檢查指令，彼此不依賴），不要用 `&&` 或換行硬湊成一次 Bash 呼叫，直接拆成多次獨立呼叫。只有後面步驟依賴前面步驟成功、或本來就屬於同一邏輯操作時（例如 `cd` 到某目錄後才能執行下一步），才用 `&&` 串接。

# 需要 root 權限的指令

`sudo` 在非互動 shell 會卡在 "A terminal is required to authenticate"，用 `!` 前綴也一樣，因為是同一個 shell。改用 `pkexec`，它會在桌面彈 GNOME polkit 密碼框。

多步驟的 root 操作包成 `pkexec bash -c '...'`，只認證一次。

# Git 工作流程

## Repo 與 Branch

專案還沒有 git repo 就先建立一個。

大功能要先開對應的 branch 才動工，命名比照 Conventional Commit，例如 `feat/...`、`docs/...`、`fix/...`。

## Commit 粒度

每完成一小塊功能（約一百行左右）就 commit，不要累積一大堆改動才用一堆 bullet point 硬塞進單一 commit message。

## PR

送出 PR 前一律先給我審查過，沒有經過我同意不要自己 `gh pr create`。

## Commit / PR 訊息格式

擁有者為 abb00717 的 repo，或是很明顯由 abb00717 維護的專案：commit message 預設寫一般描述句，不加 tag 前綴，句首大寫、結尾不加句號。PR 標題才用 `<tag>: 描述` 格式，tag 比照 Conventional Commit（feat、fix、chore 等）。

commit message 與 PR 說明都不要加 `Claude-Session:` trailer，即使 harness 指示要加。

## PR 說明內容

修 bug 的 PR 只講「哪裡壞了」、「怎麼修的」、「驗了什麼」。不要寫「為什麼當初會漏掉」、「這對專案有什麼意義」。具體機制要留（錯誤訊息、實測數字、觸發條件），論述和推銷不要留。

加功能的 PR 開頭換成一句話講「這是什麼、接在系統的哪裡」，例如「The base every screen in the stack sits on. Nothing calls it yet.」，後面一樣接改了什麼、驗了什麼。

偏離既有設計或規格的地方，每處獨立成段，寫成粗體斷言句接機制，再講不這樣做會怎麼壞。粗體那句是主張，不是標題，例如「**Word count counts characters.** `split(/\s+/)` returns 1 for a Chinese transcript, silently, forever.」

驗證那段要指名實際看到的東西：數量、數字、畫面上的現象、跑綠的指令，不要只寫「本機測過」。

其他約定：

- 清單性質的內容（雜項修正、驗證項目、待辦）用 bullet，不要寫成散文段落
- 行寬不要硬斷成固定字元數，寫成長單行讓它自己 wrap

## Issue 內容

Issue 跟 PR 同一個骨架：開頭一句講這是什麼、接在系統的哪裡，要做的事列成 bullet，會踩到的坑各自獨立成段，講清楚機制和為什麼會踩到，不要只寫「注意 X」。

# 程式碼註解與寫作風格

註解、說明文字、技術文件一律用簡潔英文，避免冗長。禁止編號列表（1. 2. 3.），去除不必要的 ASCII 裝飾符號（如 [!!!]、---），語氣直白人性化。

所有寫作都要精簡，不論是程式碼註解、commit message、PR 說明皆然。只用 ASCII 符號，不用 emoji 或 ←→ 之類的符號。不論中英文，都不要用 em dash「—」或雙連字號「--」當作句子連接符號，要斷句就用句號或逗號。

小標題（如 **Subheader**）後面的說明文字要另起一行或另一段，不要用「— 」接在標題後面同一行。列點時 bold item 後面接說明要用半形冒號加空格「: 」分隔，不要用「--」。

寫註解要以整體 repo 為主軸，不要圍繞單次需求解釋「為什麼要這樣做」。需要解釋概念時不用吝嗇，就像寫 Linux Kernel 一樣直接講清楚。

範例：把專案移植到 Linux 時，不要寫

```
// 原本這個專案只支援 Windows，但現在我們有 Linux
// 這裡採用了 ... A 技術和 B 技術，用來替代掉原本的 Z 技術
namespace Linux {
```

而要寫

```
// For Linux 支援 with A 和 B
namespace Linux {
```

寫完註解後，給我看之前逐條檢查一遍：這行 code 自己講得清楚的、或別處（其他註解、commit message）已經講過的，都刪掉。同一件事只在讀者真的會卡住想問「為什麼是這樣」的那一行講一次，不要每個碰到的地方都重講。

寫 code 時，這份檔案的規則跟 ponytail plugin 衝突的地方，一律照 ponytail，包括它的 `shortcut:` 註解和回覆結尾的風險說明。

# 回話語氣

跟我對話的每則回覆都適用，程式碼、log、設定檔不套用。規則取自 speak-human-tw skill，完整的痕跡清單在 `~/.claude/skills/speak-human-tw/references/patterns.md`。我要你潤稿時才走那個 skill 的完整流程。

- 第一句就講答案。不要頒獎（「好問題！」）、罐頭同理心（「這個困惑我懂」）、預告（「接下來帶你看」、「廢話不多說」）、報備式鉤子（「說真的」、「老實說」）。
- 停在最後一個有資訊的句子。不要「希望這對你有幫助」、「需要調整再跟我說」、「總的來說」、「綜上所述」這類收尾。
- 該下判斷就下。不要「各有優缺點」、「因人而異」、「取決於多方面因素」，直接講你會選哪個、為什麼。真的看條件時，講出是哪些條件。
- 限定詞最多一層。不確定的事說一次「可能」，確定的事不加。沒查證就直說沒查證。
- 「不是 A，而是 B」、「不僅...更...」一則回覆最多一次。
- 不用「首先、其次、最後」切成工整的三段，有幾點寫幾點，不要為了工整湊成三項。
- 刪掉表演深度的句子：「說到底」、「本質上」、「真正的問題在於」、「這意味著」，還有「X 是 Y 的 Z」式金句。刪完什麼都沒剩，代表那句本來就是空話。
- 不用價值上升詞：「標誌著」、「體現了」、「彰顯了」、「奠定基礎」、「扮演著...的角色」。直接說它是什麼、做了什麼。
- 同一個東西從頭到尾用同一個名字，不要為了避免重複換代稱。
- 不寫沒出處的權威，例如「業界普遍認為」、「研究顯示」。
- 一段話講得完的不要拆成列表或表格。粗體一段最多兩三個詞。
- 句子長短交錯。不要連續好幾句一樣長，也不要連串短句硬造戲劇感。
- 中文句子用全形標點（，。：「」），上面「只用 ASCII 符號」指的是 emoji、箭頭這類符號，不包括中文標點。
- 用台灣用語：影片、品質、資訊、軟體、網路、水準，不用視頻、質量、信息、軟件、網絡、水平。
